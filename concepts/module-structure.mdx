Every PrestaShop module is a self-contained PHP package that follows a strict set of naming and structural conventions. The PrestaShop autoloader and module manager both rely on these conventions to locate, instantiate, and lifecycle-manage your module. Understanding the layout before you write a single line of logic will save you from cryptic "module not found" errors and make your code immediately recognizable to other PrestaShop developers.

## The Golden Rule: Names Must Match

The single most important convention in PrestaShop module development is the **triple-match rule**: the directory name, the root PHP filename, and the PHP class name must all be identical (and all lowercase for the directory/file).

```text
democontrollertabs/           ← directory name
└── democontrollertabs.php    ← file name (same)
    └── class democontrollertabs  ← class name (same, case-insensitive on the class)
```

<Warning>
Violating the triple-match rule causes the module to fail silently in the Back Office module list. PrestaShop uses `$this->name` from the constructor to build file paths, so any mismatch between the constructor value, the filename, and the directory will break installation.
</Warning>

## Standard Directory Tree

A Symfony-enabled PrestaShop 9 module has the following layout:

```text
democontrollertabs/
├── democontrollertabs.php   # Module entry point and class definition
├── config.xml               # Module metadata for the BO module list (no-DB fallback)
├── composer.json            # PSR-4 autoload + dependency declarations
├── logo.png                 # 32×32 module icon shown in the BO
├── config/
│   ├── services.yml         # Symfony DI service definitions
│   └── routes.yml           # Symfony router entries for admin controllers
├── src/                     # All PSR-4 autoloaded source code
│   └── Controller/
│       └── Admin/
│           └── ConfigureController.php
└── views/
    └── templates/
        └── admin/           # Twig templates for admin pages
            └── configure.html.twig
```

<Note>
The `config/services.yml` and `config/routes.yml` files are automatically picked up by PrestaShop's Symfony kernel when the module is enabled. You do **not** need to register them manually—PrestaShop scans all active modules for these files at container compile time.
</Note>

## The Module Class Skeleton

The root PHP file defines a class that extends `Module`. Here is the complete, real skeleton from `democontrollertabs`:

```php
declare(strict_types=1);

if (!defined('_PS_VERSION_')) {
    exit;
}

// Needed for install process before the Symfony container is available
require_once __DIR__ . '/vendor/autoload.php';

use PrestaShop\Module\DemoControllerTabs\Controller\Admin\ConfigureController;
use PrestaShop\Module\DemoControllerTabs\Controller\Admin\ManualTabController;

class democontrollertabs extends Module
{
    public function __construct()
    {
        $this->name = 'democontrollertabs';
        $this->author = 'PrestaShop';
        $this->version = '1.0.0';
        $this->ps_versions_compliancy = ['min' => '9.0.0', 'max' => '9.99.99'];

        parent::__construct();

        $this->displayName = $this->trans('Demo Controller Tabs', [], 'Modules.Democontrollertabs.Admin');
        $this->description = $this->trans('Demonstration of Symfony Controllers, Tabs and Permissions', [], 'Modules.Democontrollertabs.Admin');

        $tabNames = [];
        foreach (Language::getLanguages(true) as $lang) {
            $tabNames[$lang['locale']] = $this->trans('Demo Controller Tabs', [], 'Modules.Democontrollertabs.Admin', $lang['locale']);
        }
        $this->tabs = [
            [
                'route_name' => 'ps_controller_tabs_configure',
                'class_name' => ConfigureController::TAB_CLASS_NAME,
                'visible' => true,
                'name' => $tabNames,
                'icon' => 'school',
                'parent_class_name' => 'IMPROVE',
            ],
        ];
    }

    public function getContent()
    {
        Tools::redirectAdmin(
            $this->context->link->getAdminLink(ConfigureController::TAB_CLASS_NAME)
        );
    }

    public function install()
    {
        return parent::install() && $this->manuallyInstallTab();
    }
}
```

<CardGroup cols={2}>
  <Card title="Constructor Properties" icon="wrench">
    Set `name`, `author`, `version`, and `ps_versions_compliancy` **before** calling `parent::__construct()`. The parent constructor reads `$this->name` to load translations and configuration, so order matters.
  </Card>
  <Card title="Display Properties" icon="eye">
    Set `displayName` and `description` **after** `parent::__construct()` because they use `$this->trans()`, which requires the translation context the parent sets up.
  </Card>
  <Card title="install() / uninstall()" icon="download">
    Always chain `parent::install()` first. These methods create the database row in `ps_module`, register permissions, and handle hook registrations. A missing `parent::install()` call leaves your module in a broken half-installed state.
  </Card>
  <Card title="getContent()" icon="gear">
    Called when the admin clicks "Configure" in the module list. For Symfony-based modules it typically issues a redirect to the Symfony controller route rather than rendering HTML directly.
  </Card>
</CardGroup>

## config.xml

`config.xml` acts as a static metadata cache. PrestaShop reads it to populate the module list **before** instantiating the PHP class, which avoids loading every module's PHP just to display names and descriptions.

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<module>
    <name>democontrollertabs</name>
    <displayName><![CDATA[Demo Controller Tabs]]></displayName>
    <version><![CDATA[1.0.0]]></version>
    <description><![CDATA[Demonstration of Symfony Controllers, Tabs and Permissions]]></description>
    <author><![CDATA[PrestaShop]]></author>
    <tab><![CDATA[]]></tab>
    <is_configurable>1</is_configurable>
    <need_instance>1</need_instance>
</module>
```

<Tip>
Keep `config.xml` in sync with your module class. The `<version>` tag is compared against the database during upgrades—a mismatch will trigger the upgrade wizard in the Back Office.
</Tip>

Key fields:

| Field | Purpose |
|---|---|
| `<name>` | Must match `$this->name` in the class constructor |
| `<version>` | Shown in the BO; triggers upgrade detection |
| `<is_configurable>` | Shows/hides the "Configure" button in the module list |
| `<need_instance>` | Whether PrestaShop instantiates the module class on every page load |

## composer.json and PSR-4 Autoloading

All source classes under `src/` are loaded via Composer's PSR-4 autoloader. The namespace root maps to the `src/` directory:

```json
{
  "name": "prestashop/democontrollertabs",
  "license": "AFL-3.0",
  "require": {
    "php": ">=8.1"
  },
  "autoload": {
    "psr-4": {
      "PrestaShop\\Module\\DemoControllerTabs\\": "src/"
    }
  },
  "config": {
    "prepend-autoloader": false
  },
  "type": "prestashop-module"
}
```

<Note>
`"prepend-autoloader": false` is required. PrestaShop registers its own autoloader first; prepending the module autoloader would break core class resolution for legacy classes that don't use namespaces.
</Note>

After adding or changing the namespace mapping, run:

```bash
composer dump-autoload
```

The generated `vendor/autoload.php` must be `require_once`'d at the top of your root PHP file (before `class` declaration) so it is available during the `install()` phase, when the Symfony container is not yet compiled.

## The `src/` Directory

All domain logic, controllers, forms, repositories, and entities live under `src/`. The PSR-4 namespace you declare in `composer.json` is the root, and subdirectory names become namespace segments:

```text
src/
├── Controller/
│   └── Admin/
│       └── ConfigureController.php   → PrestaShop\Module\DemoControllerTabs\Controller\Admin\ConfigureController
├── Form/
│   └── ConfigureFormType.php         → PrestaShop\Module\DemoControllerTabs\Form\ConfigureFormType
└── Repository/
    └── FooRepository.php             → PrestaShop\Module\DemoControllerTabs\Repository\FooRepository
```

## views/templates/admin/

Twig templates for Back Office pages live in `views/templates/admin/`. They are referenced from controllers using the `@Modules/` namespace alias:

```php
return $this->render('@Modules/democontrollertabs/views/templates/admin/configure.html.twig');
```

PrestaShop registers this alias automatically for every enabled module, mapping `@Modules/{module_name}/` to the module's root directory.
